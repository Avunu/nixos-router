# Settings format & migrations

A router's configuration lives in `/etc/nixos/router-settings.json`, the file Cockpit edits. The host flake (`/etc/nixos/flake.nix`) hands that file to the router module.

The module's options sometimes change shape between versions. For example, port forwards used to name an IPv4 `destination` and now name a registered `host`. So the host flake must read the file **through `nixos-router.lib`**, which upgrades settings written for an older version on the way in:

```nix
settings = nixos-router.lib.readSettings ./router-settings.json;
...
modules = [
  nixos-router.nixosModules.router
  (nixos-router.lib.settingsModule ./router-settings.json)
  # ... locked settings module ...
];
```

New deployments get this automatically:

-   `local/flake.nix` (network deploys) calls the loader directly.
-   The flake an ISO install seeds (generated by nixos-install-helper) loads each settings file through `nixos-router.lib.settingsModules.router`, the same loader.

## One-time update for existing routers

Routers deployed before the loader existed read the JSON directly. Their `flake.nix` has these two lines:

```nix
settings = builtins.fromJSON (builtins.readFile ./router-settings.json);
...
{ router = nixpkgs.lib.mkDefault settings; }
```

A router installed from an older ISO has a line like this instead:

```nix
{ router = load "router"; }
```

On such a router, an upgrade that changes an option's shape fails with an error like `The option router.portForwards."[definition 1-entry 1]".destination does not exist`. The running system is unaffected: nothing is switched. Fix it once in `/etc/nixos/flake.nix`:

1.  Replace the settings module line, either `{ router = nixpkgs.lib.mkDefault settings; }` or `{ router = load "router"; }`, with `(nixos-router.lib.settingsModule ./router-settings.json)`.
2.  If the file has a `settings = builtins.fromJSON (…);` line, replace it with `settings = nixos-router.lib.readSettings ./router-settings.json;`.
3.  Run `system-upgrade` again.

## What happens during an upgrade

-   **Rebuild.** The settings are upgraded in memory while the configuration is evaluated, so the rebuild succeeds and the router behaves as it did before.
-   **File rewrite.** If anything was upgraded, activation rewrites `router-settings.json` into the current format. The previous file is kept as `router-settings.json.pre-migration`. From then on, Cockpit only ever sees the current format.
-   **Edits are safe.** The rewrite only happens if the file is still exactly what the build read. A file edited in the meantime is left alone, and it is upgraded on the next rebuild instead.
-   **Unresolvable entries stop the build.** If an old entry cannot be upgraded unambiguously, the build stops with a message saying what to fix, and the running system is left untouched. For example, an old port forward whose address no registered host reserves as its `staticIp` stops the build. In that case, register the device, then rebuild.

## Adding a migration (maintainers)

When a change renames, removes, or reshapes a `router.*` option that settings JSON can carry:

1.  Change the option to the new shape only. Don't keep the retired option alive in the module.
2.  Append a migration to `migrations` in `lib/settings.nix`. It is a function from the raw settings attrset to the upgraded attrset, and it must:
    -   pass JSON that is already current through unchanged, because every migration runs on every evaluation;
    -   `throw` an actionable message rather than guess, when an entry cannot be upgraded.
3.  Cover the migration in `tests/settings-loader.nix`: the old shape upgraded, current JSON untouched, and idempotence.
